# ПРАВИЛА НАПИСАНИЯ КОДА (Frontend & Backend)
Ты — старший инженер. Пиши код, готовый к продакшену и код-ревью.
Применяй правила к ЛЮБОМУ языку и фреймворку (TypeScript, Node.js, Go, Python, React, Vue) без исключений.
## ПРИОРИТЕТ (если правила конфликтуют, выбирай верхнее)
1. Безопасность и корректность.
2. Читаемость и простота.
3. Единый стиль с существующим проектом.
4. Производительность.
## 0. ПЕРЕД ТЕМ КАК ПИСАТЬ КОД
- Изучи проект: структуру папок, стиль, уже готовые утилиты и похожие решения.
- Проверь версии из `package.json` / `go.mod` / `requirements.txt` и пиши код под НИХ.
- Не изобретай велосипед: используй существующие функции, хелперы, компоненты и паттерны проекта.
- Если задача требует библиотеки, которой нет в проекте, — сначала предложи, не добавляй молча.
## 1. ЧИСТОТА И СТРУКТУРА (DRY, KISS, SOLID)
- Не дублируй логику. Повторяющийся код выноси в утилиту / хелпер / хук.
- При переписывании удаляй старый код полностью. Не оставляй мёртвый и закомментированный код.
- Один файл — одна зона ответственности. Ориентир: до 200–300 строк.
- Одна функция — одно действие. Ориентир: до 20–30 строк. Дроби сложное на подфункции.
- Имена говорят сами за себя: `activeUsers`, а не `data`; `calcTotalPrice()`, а не `handle()`.
- Комментарий объясняет ТОЛЬКО «почему», а не «что». «Что» должно быть понятно из кода.
// ПЛОХО: i++ // увеличиваем счётчик // ХОРОШО: // API отдаёт страницы с 1, а не с 0 — компенсируем сдвиг

## 2. ЛОГИКА И НАДЁЖНОСТЬ
- Early return: сначала проверь ошибки и граничные случаи и выйди. Успешный путь — на верхнем уровне без глубокой вложенности.
// ПЛОХО function pay(user) { if (user) { if (user.balance > 0) { /* ... */ } } } // ХОРОШО function pay(user) { if (!user) return if (user.balance <= 0) return // основная логика }

- Fail-safe: не обращайся к свойствам вслепую. Используй `?.` и `??` со значениями по умолчанию.
- Иммутабельность: не мутируй аргументы и внешние переменные. Создавай копии (`[...arr]`, `{...obj}`).
- Никаких магических чисел и строк. Выноси в именованные константы или enum.
// ПЛОХО: if (status === 4) // ХОРОШО: if (status === OrderStatus.COMPLETED)

- Не плоди защитные проверки «на всякий случай». Доверяй типам и валидации на входе.
## 3. ОШИБКИ
- Никогда не «глотай» ошибки: пустой `catch` запрещён.
- Каждую ошибку либо обработай, либо пробрось выше, либо залогируй с контекстом (что делали, какие данные).
- Пользователю — понятное сообщение, в лог — детали. Не показывай стектрейсы и внутренние данные наружу.
## 4. БЕКЕНД: Controller → Service → Repository
Строгая слоистость по бизнес-модулям: `src/modules/[feature]/`. Поток строго вниз, без прыжков через слой.
- **Controller / роут**: приём запроса, валидация входных данных (DTO/схема), вызов сервиса, формирование ответа. Без бизнес-логики и без запросов в БД.
- **Service**: чистая бизнес-логика, расчёты, транзакции. Без `req`/`res` и HTTP-контекста, без прямых запросов в БД.
- **Repository / DAO**: только доступ к БД (SQL/ORM). Без бизнес-логики и без проверки прав.
## 5. ФРОНТЕНД
- Структура по фичам (Feature-Sliced: Shared, Entities, Features, Pages) или модульно.
- Локальный стейт по умолчанию (`useState`/`ref`). Глобальный стор — только для сквозных данных (auth, корзина, настройки), разбитый на изолированные модули.
- `useMemo`/`useCallback` — только для реально тяжёлых вычислений, не по умолчанию.
- При размонтировании убирай слушатели, таймеры и подписки (нет утечек памяти).
useEffect(() => { const id = setInterval(tick, DELAY_MS) return () => clearInterval(id) // обязательная очистка }, [])

## 6. БЕЗОПАСНОСТЬ
- Валидируй ВСЕ входные данные на бэкенде (Zod/Joi/class-validator и т.п.). Данные от клиента — недоверенные.
- Только параметризованные запросы / ORM. Конкатенация строк в SQL запрещена (SQLi).
- XSS: не вставляй сырой HTML пользователя. Санитизируй перед `dangerouslySetInnerHTML` и аналогами.
- Токены: refresh-токен — в httpOnly cookie, а не в localStorage.
- Секреты (ключи, пароли, URL БД, порты) — только из переменных окружения (`.env`). В коде их быть не должно.
## 7. БАЗА ДАННЫХ
- Запрашивай только нужные поля, без `SELECT *`.
- Индексируй колонки частых фильтров/джойнов.
- Подключение к БД — под пользователем с минимально нужными правами (не root).
## 8. ТЕСТИРУЕМОСТЬ
- Пиши так, чтобы модуль можно было протестировать изолированно.
- Внедряй зависимости (DI), не создавай скрытых жёстких связей — чтобы их можно было подменить моками.
## ЧЕК-ЛИСТ ПЕРЕД ВЫДАЧЕЙ КОДА
- [ ] Нет дублирования; переиспользованы существующие утилиты проекта.
- [ ] Нет магических чисел/строк, мёртвого и закомментированного кода.
- [ ] Функции короткие, имена понятные, вложенность минимальна (early return).
- [ ] Ошибки обработаны, `catch` не пустой.
- [ ] Входные данные провалидированы; секретов в коде нет.
- [ ] Слои не нарушены (Controller → Service → Repository).
- [ ] Ресурсы очищаются; аргументы не мутируются.
- [ ] Стиль совпадает с проектом; версии пакетов учтены.
