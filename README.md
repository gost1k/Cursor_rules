# Cursor_rules

# СТРОГИЕ ПРАВИЛА РАЗРАБОТКИ И АРХИТЕКТУРЫ (FRONTEND & BACKEND)

## 1. Чистота кода и организация (DRY, KISS, SOLID)
- **Zero-Duplication:** Запрещено дублировать код. При переписывании логики старый код должен быть полностью удален или заменен новым.
- **KISS & Читаемость:** Пиши максимально простой, сжатый код, который читается как текст. Избегайте сложных "умных" однострочников, ухудшающих понимание.
- **Разумные проверки:** Не плоди лишние `if/else` и проверки "на всякий случай". Доверяй типам данных и валидации на входе.
- **Single Responsibility:** 
  - Один файл — одна задача (максимум 200–300 строк).
  - Одна функция — одно действие (максимум 20–30 строк). Дроби сложную логику на подфункции.
- **Контекст приложения:** Всегда изучай текущий проект перед написанием нового кода. Пиши в едином стиле, не изобретай новые велосипеды в рамках существующей экосистемы.
- **Читаемость кода:** В первую очередь код должен быть хорошо организован и легко читаем, а уже потом функциональность. Переменные должны характеризовать то, что они делают.

## 2. Логика, Условия и Безопасность кода
- **Early Return:** Избегай глубокой вложенности условий. Сначала проверяй ошибочные/пограничные случаи и сразу выходи из функции (`return` или `throw`). Основной успешный код должен идти на верхнем уровне.
- **Fail-Safe (Защита от падений):** Запрещено обращаться к свойствам объектов "вслепую". Всегда используй безопасную навигацию (optional chaining `?.`) и значения по умолчанию (nullish coalescing `??`).
- **Иммутабельность:** Функции не должны менять переданные аргументы или глобальные переменные. Для изменения массивов/объектов создавай их копии (`[...arr]`, `{...obj}`).
- **No Magic Values:** Запрещено использовать жестко зашитые "магические" числа или строки. Выноси их в именованные константы или Enums (например, `STATUS.COMPLETED = 4`).
- **Самодокументируемость:** Код должен объяснять себя сам понятными именами переменных и функций. Комментарии нужны только для объяснения *ПОЧЕМУ* выбрано нестандартное решение (например, обход бага библиотеки).

## 3. Бекенд: Архитектура Controller-Service-Repository
Строго разделяй код по папкам бизнес-модулей (Feature-driven): `src/modules/[feature_name]/`. 
Поток вызовов строго линеен: **Controller ➡️ Service ➡️ Repository**. Прыжки через слой или обратные вызовы запрещены.
- **Controller (`*.controller.*` или роуты):** Только прием трафика, валидация входных данных (DTO/схемы) и вызов Сервиса. Бизнес-логика и прямые запросы к БД здесь запрещены.
- **Service (`*.service.*`):** Чистая бизнес-логика, расчеты, транзакции. Запрещено использовать объекты веб-фреймворка (req, res, http-контекст) и делать прямые запросы к БД.
- **Repository (`*.repository.*` или DAO):** Только прямая работа с БД (SQL, ORM, драйверы). Запрещено логировать бизнес-логику или проверять права доступа.

## 4. Фронтенд: Архитектура и Оптимизация
- **Структура:** Используй модульный подход или методологию Feature-Sliced Design (Shared, Entities, Features, Pages).
- **State Management:** Глобальный стор (Redux, Zustand, Pinia) — только для сквозных данных (авторизация, корзина) с делением на изолированные модули. Для остального — строго локальный стейт.
- **Очистка ресурсов:** Всегда удаляй слушатели событий, таймеры и отписывайся от потоков данных при размонтировании компонентов (предотвращение утечек памяти).
- **Мемоизация:** Используй хуки/методы оптимизации рендеринга (`useMemo`, `useCallback`) только для действительно тяжелых вычислений.

## 5. Инфраструктура, Безопасность и Тесты
- **12-Factor App (Конфигурация):** Никакие доступы, ключи API, порты, URL-адреса баз данных не должны находиться в коде. Считывай их строго из переменных окружения (`.env`).
- **Обработка ошибок:** Запрещено "проглатывать" ошибки (пустые `catch`). Каждая ошибка должна быть обработана, записана в логгер с контекстом или проброшена выше.
- **Защита данных:** Валидируй все входящие данные на бэкенде. Используй параметризованные запросы/ORM для защиты от SQLi. На фронтенде делай очистку (санитизацию) HTML и храни токены в `httpOnly` cookies.
- **Testability:** Пиши код так, чтобы его было легко протестировать изолированно. Избегай жестких скрытых зависимостей, используй Dependency Injection, чтобы зависимости можно было легко подменить на моки в Unit-тестах.

## 6. Оптимизация рендеринга
Оптимизация рендеринга: Избегайте лишних перерендеров. Используйте мемоизацию (useMemo, useCallback) там, где выполняются тяжелые вычисления.Очистка ресурсов: Всегда удаляйте слушатели событий (addEventListener), таймеры (setTimeout) и отписывайтесь от потоков данных при размонтировании компонентов (предотвращение утечек памяти).Защита от XSS: Никогда не вставляйте сырой HTML от пользователя без санитизации (очистки). Избегайте бездумного использования dangerouslySetInnerHTML (или аналогов).Безопасное хранение токенов: Токены авторизации (Refresh token) должны храниться в безопасных httpOnly cookies, а не в LocalStorage, чтобы их нельзя было украсть через JS-скрипты.

## 7. Хранилища
Минимализм сторов: Не создавайте глобальный стор (Redux, Pinia, Zustand) для всего подряд.Локальный стейт прежде всего: Если данные нужны только одному компоненту и его дочерним элементам — используйте локальный стейт (useState, ref).Разделение на модули: Глобальный стор создается только для сквозных данных (авторизация, корзина, настройки профиля) и строго делится на изолированные модули (slices/modules).

## 8. Обработка данных
Валидация на входе: Никакой сырой код от клиента не должен идти в базу. Используйте DTO и библиотеки валидации (Zod, Joi, Class-validator или другую).Безопасность БД: Использование только параметризованных запросов или ORM для защиты от SQL-инъекций.Принцип наименьших привилегий: Приложение должно подключаться к БД с минимально необходимыми правами (не под root-пользователем).Индексация БД: Любой частый запрос в БД должен быть оптимизирован индексами. Избегайте SELECT *, запрашивайте только нужные поля.Логирование и мониторинг: Ошибки не должны "проглатываться". Используйте централизованное логирование (Winston, Pino) и корректные HTTP-статусы (400, 401, 403, 404, 500).

## 9. Частота кода.
Удаление дубликатов: Запрещено писать код, который повторяет существующую логику.Замена старого кода: При переписывании функционала старый код должен быть полностью удален или заменен новым.Переиспользование: Выносите общую логику в утилиты (utils), хелперы или кастомные хуки/функции.

Перед написанием нового кода изучите, как подобные задачи уже решены в проекте. Use-cases, стилистика и подходы должны быть едиными. Не изобретайте новые велосипеды в рамках существующей экосистемы.
