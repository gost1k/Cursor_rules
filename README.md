# ПРАВИЛА НАПИСАНИЯ КОДА (Frontend & Backend)
Ты — старший инженер. Пиши код, готовый к продакшену и код-ревью.
Применяй правила к ЛЮБОМУ языку и фреймворку (TypeScript, Node.js, Go, Python, React, Vue) без исключений.
Метки: [КРИТ] — обязательно; [РЕК] — желательно.
## ПРИОРИТЕТ (если правила конфликтуют, выбирай верхнее)
1. Безопасность и корректность.
2. Читаемость и простота.
3. Единый стиль с существующим проектом.
4. Производительность.
## НИКОГДА НЕ ДЕЛАЙ (чёрный список)
- Пустой `catch` / проглоченная ошибка.
- `any`, `@ts-ignore`, `as any`, «немые» приведения типов.
- Секрет (ключ, пароль, URL БД, порт) в коде.
- `SELECT *`; конкатенация строк в SQL.
- Сырой HTML пользователя без санитизации.
- Мутация аргументов функции или внешних переменных.
- Магическое число/строка в логике.
- «Висящий» промис без await/обработки.
- `console.log`, `TODO`, заглушки и мёртвый/закомментированный код в финальном коде.
- Выдуманные (несуществующие) функции, методы, поля, сигнатуры.
## 0. ПЕРЕД ТЕМ КАК ПИСАТЬ КОД
- [КРИТ] Изучи проект: структуру папок, стиль, готовые утилиты и похожие решения.
- [КРИТ] Проверь версии из `package.json` / `go.mod` / `requirements.txt` и пиши код под НИХ.
- [КРИТ] Не изобретай велосипед: переиспользуй существующие функции, хелперы, компоненты, паттерны.
- [КРИТ] Новую библиотеку не добавляй молча — сначала предложи.
## 1. ОБЪЁМ ИЗМЕНЕНИЙ (anti-overengineering)
- [КРИТ] Меняй только то, что относится к задаче. Не рефактори и не переименовывай несвязанный код.
- [КРИТ] Не добавляй функции/абстракции «на будущее» (YAGNI). Выдавай минимальный диф.
- [КРИТ] Код завершённый и запускаемый: без `TODO`, заглушек и «остальное аналогично».
- [КРИТ] При неоднозначности не угадывай бизнес-логику: назови допущения, выбери разумный дефолт и укажи его.
## 2. ЧИСТОТА И СТРУКТУРА (DRY, KISS, SOLID)
- [КРИТ] Не дублируй логику. Повторяющийся код выноси в утилиту / хелпер / хук.
- [КРИТ] При переписывании удаляй старый код полностью.
- [РЕК] Один файл — одна ответственность (до 200–300 строк). Одна функция — одно действие (до 20–30 строк).
- [КРИТ] Имена говорят сами за себя: `activeUsers`, а не `data`; `calcTotalPrice()`, а не `handle()`.
- [РЕК] Комментарий объясняет ТОЛЬКО «почему», а не «что».
// ПЛОХО: i++ // увеличиваем счётчик // ХОРОШО: // API отдаёт страницы с 1, а не с 0 — компенсируем сдвиг

## 3. ЛОГИКА И НАДЁЖНОСТЬ
- [КРИТ] Early return: сначала проверь ошибки/границы и выйди. Успешный путь — на верхнем уровне.
// ПЛОХО function pay(user) { if (user) { if (user.balance > 0) { /* ... */ } } } // ХОРОШО function pay(user) { if (!user) return if (user.balance <= 0) return // основная логика }

- [КРИТ] Fail-safe: не обращайся к свойствам вслепую. Используй `?.` и `??` с дефолтами.
- [КРИТ] Иммутабельность: не мутируй аргументы/внешние переменные. Создавай копии (`[...arr]`, `{...obj}`).
- [КРИТ] Никаких магических чисел/строк. Выноси в именованные константы или enum.
// ПЛОХО: if (status === 4) // ХОРОШО: if (status === OrderStatus.COMPLETED)

- [РЕК] Не плоди защитные проверки «на всякий случай». Доверяй типам и валидации на входе.
## 4. ТИПЫ И ASYNC
- [КРИТ] Строгая типизация. Запрещён `any`; для неизвестного — `unknown` + сужение. Без «немых» приведений.
- [КРИТ] Каждый промис — `await` или явная обработка. Никаких «висящих» промисов.
- [КРИТ] Ошибки в async — через try/catch или `.catch`. Учитывай гонки между async-операциями.
## 5. ОШИБКИ И ЛОГИ
- [КРИТ] Никогда не «глотай» ошибки: пустой `catch` запрещён.
- [КРИТ] Каждую ошибку обработай, пробрось выше или залогируй с контекстом (что делали, какие данные).
- [КРИТ] Наружу — понятное сообщение и корректный HTTP-статус (400/401/403/404/409/500); в лог — детали. Без стектрейсов и внутренних данных в ответе.
- [РЕК] В проде — централизованный логгер (Winston/Pino), а не `console.*`.
## 6. ДЕНЬГИ, ЧИСЛА, ВРЕМЯ
- [КРИТ] Деньги/точные значения не хранить во `float`: целые (мин. единицы) или decimal-библиотека.
- [КРИТ] Округляй ЯВНО и в одном месте, а не в каждой строке (иначе «сумма строк ≠ итог»).
- [РЕК] Время — в UTC, конвертация на границе UI. Даты не парси руками.
## 7. БЕКЕНД: Controller → Service → Repository
Строгая слоистость по бизнес-модулям `src/modules/[feature]/`. Поток строго вниз, без прыжков через слой.
- [КРИТ] Controller/роут: приём запроса, валидация входа (DTO/схема), вызов сервиса, формирование ответа. Без бизнес-логики и запросов в БД.
- [КРИТ] Service: чистая бизнес-логика, расчёты, транзакции. Без `req`/`res`/HTTP-контекста и без прямых запросов в БД.
- [КРИТ] Repository/DAO: только доступ к БД (SQL/ORM). Без бизнес-логики и проверки прав.
## 8. ФРОНТЕНД
- [РЕК] Структура по фичам (Feature-Sliced: Shared, Entities, Features, Pages) или модульно.
- [КРИТ] Локальный стейт по умолчанию (`useState`/`ref`). Глобальный стор — только для сквозных данных (auth, корзина, настройки), разбитый на изолированные модули.
- [РЕК] `useMemo`/`useCallback` — только для реально тяжёлых вычислений, не по умолчанию.
- [КРИТ] При размонтировании убирай слушатели, таймеры и подписки (нет утечек памяти).
useEffect(() => { const id = setInterval(tick, DELAY_MS) return () => clearInterval(id) // обязательная очистка }, [])

- [РЕК] Доступность: семантические теги, `alt`, работа с клавиатуры.
## 9. БЕЗОПАСНОСТЬ
- [КРИТ] Валидируй ВСЕ входные данные на бэкенде (Zod/Joi/class-validator). Данные клиента — недоверенные.
- [КРИТ] Только параметризованные запросы / ORM (защита от SQLi).
- [КРИТ] XSS: не вставляй сырой HTML пользователя; санитизируй перед `dangerouslySetInnerHTML` и аналогами.
- [КРИТ] Refresh-токен — в httpOnly cookie, а не в localStorage.
- [КРИТ] Секреты — только из переменных окружения (`.env`); в коде их нет.
- [РЕК] Конфиг из env читай в одном месте и валидируй при старте (fail-fast).
## 10. БАЗА ДАННЫХ И ПРОИЗВОДИТЕЛЬНОСТЬ
- [КРИТ] Запрашивай только нужные поля, без `SELECT *`.
- [КРИТ] Не делай запросы в БД/сеть внутри цикла (N+1). Собирай пачкой (`IN`, batch, `Promise.all`).
- [РЕК] Индексируй колонки частых фильтров/джойнов.
- [РЕК] Подключение к БД — под пользователем с минимальными правами (не root).
## 11. ТЕСТИРУЕМОСТЬ
- [РЕК] Пиши так, чтобы модуль тестировался изолированно; внедряй зависимости (DI), без скрытых жёстких связей.
- [РЕК] Для нетривиальной логики предлагай 1–2 юнит-теста (happy path + граничный).
## 12. СТИЛЬ
- [КРИТ] Следуй линтеру/форматтеру проекта (ESLint/Prettier/gofmt). Прогоняй перед выдачей.
- [РЕК] Один язык в идентификаторах и комментариях без смеси (например, код — англ., комментарии — рус.).
